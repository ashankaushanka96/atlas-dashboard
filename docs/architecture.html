SRE Dashboard Architecture
System Architecture

SRE Dashboard

A monitoring platform for a fleet of servers/services: a small Python agent (All-in-One Watcher) runs on every monitored host, restarts local processes that die, and pushes status into the Aggregator. The React frontend pulls everything else from the Backend, which also polls live AWS resource data and Datadog, and acts as the remote control plane for the whole watcher fleet.

What each component does

Edge & client
Browserclient

The SRE engineer's session. Signs in, holds the auth token, and reaches every other service through Nginx over HTTPS/WSS — never talks to Backend or Aggregator directly.

talks to Nginx
Nginxnginx:alpine

The single TLS-terminating entry point. Redirects :80 → :443, then routes by path: static app to Frontend, the live component WebSocket to Aggregator, and every other /api/v1/* call to Backend.

talks to Frontend, Backend, Aggregator
Application services
FrontendReact + Vite

The dashboard itself, built to static files and served from an nginx:alpine container.

  • Home, ComponentDB, ComponentMap (live topology), HostDetails
  • AWSResources, EC2Schedules, Route53, ServerHandler, WatcherStatus, Pipelines
  • Pulls REST data from Backend; opens a same-origin WebSocket straight to Aggregator for live status
talks to Backend (REST), Aggregator (WS)
BackendFastAPI · :8080

The main API and the system's control plane. It is the only service that talks to AWS and Datadog — the Aggregator never does.

  • Authentication (Entra SSO), component DB/tree, table preferences
  • EC2 schedules and start/stop ("Server Handler"), Route53
  • Live read-through summaries for Lambda, ECS, EKS, MSK, Redis, load balancers, ElastiCache (via boto3)
  • Datadog metrics queries; ~17 background cache-refresh loops against Redis
  • Watcher Control: drives each host's Local Watcher API to restart processes, edit config.ini, and tail/grep/download logs
talks to MySQL, Redis, AWS APIs, Datadog, every host's Local Watcher API
AggregatorFastAPI · :8000

The ingest side — the other half of the split that makes this a monitoring system rather than just a dashboard. It only ever talks to MySQL, Redis, and the watcher fleet.

  • Receives a status POST from every host's Watcher agent
  • Maintains the live component tree in MySQL
  • Fans it back out to the browser over the /component/ws-component-details WebSocket
talks to MySQL, Redis, every host's Watcher agent (inbound)
Data stores
MySQL — COMPONENT_DBmysql:8.0

Shared system of record for Backend and Aggregator: components, EC2 schedules, users/roles, watcher-control audit trail, table preferences.

read/written by Backend, Aggregator
Redisredis:alpine

Shared cache in front of AWS API calls, schedules, and component summaries, so the dashboard doesn't re-poll AWS on every page load.

read/written by Backend, Aggregator
Fleet agent — runs on every monitored host
All-in-One WatcherPython agent

Installed on each server being monitored, driven by that host's own config.ini.

  • Checks each configured process is running; restarts it if it isn't and needToUp is set
  • Tracks CPU, memory, uptime, log-directory size and port availability
  • Pushes a status snapshot to the Aggregator every cycle
  • Sends metrics to Datadog and, on failure, an email alert via AWS SES
talks to Aggregator (push), Datadog, AWS SES
Local Watcher APIFastAPI sidecar

A small, API-key-authenticated HTTP server the agent exposes on the same host, so Backend's Watcher Control section can act on it remotely.

  • Start / stop / restart the watcher itself, or a single component via its own run.sh / kill.sh / restart.sh
  • Rewrite config.ini (add/remove components) and roll back to the last backup
  • Tail, page, grep and download a component's log files — including a live tail -f over WebSocket
called by Backend
External integrations
AWS APIsboto3

Polled live by Backend only for EC2, ECS, EKS, Lambda, MSK, ElastiCache, load balancer and Route53 detail and summary data, then cached in Redis.

Datadogmetrics API

Receives process/resource/log-size metrics pushed by every Watcher agent; Backend separately queries Datadog's metrics API to surface configured queries on the dashboard.

AWS SESSMTP

Outbound relay the Watcher agent uses to email an alert when a monitored process is found down and needToSendMail is enabled.

Built from docker-compose.yml, nginx/default.conf, and the FastAPI app wiring in backend/backend.py and aggregator/aggregator.py, plus the watcher's own app/services/aggregator.py and app/api/server.py. The Backend↔Frontend↔Nginx trio ships together via docker-compose; the All-in-One Watcher is deployed independently onto each monitored host and is not part of that compose stack.
